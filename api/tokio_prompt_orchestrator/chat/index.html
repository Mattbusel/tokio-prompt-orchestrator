Structured chat requests: what a client asked for, carried to the worker.

ModelWorker::infer takes one prompt string, which is enough for “answer this text” but loses everything else a chat client sends. ChatRequest keeps it: the model name, the messages as the client wrote them (including assistant tool_calls and tool results), and the sampling and output settings (temperature, top_p, max_tokens / max_completion_tokens, stop, seed, response_format, tools, tool_choice, parallel_tool_calls).

ModelWorker::chat answers one with a ChatResponse, which carries the text, any tool calls the model made, the finish reason and the provider’s token usage. OpenAiWorker sends the request to /chat/completions field for field, AnthropicWorker translates it to the Messages API, and LlamaCppWorker sends it to llama.cpp’s OpenAI-compatible /v1/chat/completions. Workers that do not override chat get a default that flattens the messages into one prompt and calls infer, so the settings are ignored there.

The OpenAI-compatible HTTP endpoint (POST /v1/chat/completions, feature web-api) builds a ChatRequest for every call and runs it through the pipeline, so the stage’s circuit breaker, timeout, retries and concurrency limit apply exactly as they do to plain prompts.

§Deduplication

ChatRequest::dedup_key is a SHA-256 over a canonical encoding of everything that changes the answer: the route, the model, the messages, the tools and tool choice, every sampling setting and the response format. Object keys are sorted first, so two clients that send the same request with fields in a different order share one answer, while two requests that differ in any setting never do. ChatRequest::is_cacheable says whether a completed answer may be reused after the call finishes: not when temperature > 0 without a seed, because the client asked for a sampled answer.
